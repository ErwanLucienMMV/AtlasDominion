# Phase 6 — modular backup worker

The independent Node worker supports the registry's `stopped-volume` strategy for any compatible instance. No game names are embedded in worker logic. It never stops or starts a game automatically. Schedules run independently of game uptime; running, abnormal-exit, missing, identity-mismatched and unavailable containers produce failure reports and are retried on the next interval.

## Configuration and deployment gates

Review `infrastructure/backup/settings.example.json` and `compose.json`. Paths are protected worker configuration, never registry or Discord input. Each job names a registered instance, approved source mount, Docker volume name and container mount destination, archive destination, interval, minimum free bytes and retention count. Example values are illustrative, not approved host policy. Multiple jobs need non-overlapping source and destination directories. Add approved read-only volume mounts for additional instances; no worker source change is required.

Before deployment obtain approval for host paths, capacity, schedule, retention, image, privileges and volume permissions. Build a reviewed image containing this repository and its pinned dependencies; no image is downloaded automatically. Configure the controller with `backupLockDirectory: "/locks"` and merge `infrastructure/backup/controller.override.json` with its existing application/monitoring configuration. Both processes MUST mount the identical pre-created host lock directory, with permissions allowing both UIDs to create/remove locks. Never enable the worker against a controller lacking this setting. Older deployments remain compatible but are not safe for coordinated backups until configured.

The worker has no network, public listener or lifecycle command. Dockerode inspections use the controller's existing label, identity, port and isolation validation. The socket mount grants Docker-level host privileges despite `read_only: true`; it is not a read-only API restriction. This trust expansion requires explicit deployment review. A future restricted inspection transport may reduce that privilege. Source mounts are read-only and destinations must reside separately from active data. Host ancestor directories, registry, configuration and archive storage must be trusted and not writable by game processes. Only regular files and directories are supported; links, special files and unsafe portable path names fail closed. Modes/ownership are not archived; restored files use restrictive permissions and need operator ownership review.

## Consistency, scheduling and verification

Atomic persistent per-instance directories coordinate controller lifecycle work and worker copying. Locks have no expiry. A crash, forced shutdown or storage-release failure leaves a lock requiring operator investigation; neither controller restart nor scheduler restart removes it. Before authorizing removal, confirm both processes and any underlying Docker operation have settled and no copy is active. Do not remove locks based only on age. Direct Docker/Compose administrators bypass application coordination and must not start, replace or mutate worlds during backups.

The worker requires clean `exited` state with exit code zero, checks expected volume identity, inventories files with SHA-256, checks space for copy plus restoration and configured headroom, writes a unique archive directory, and compares source contents again. It reinspects pinned container identity/state, verifies every archived path/byte, restores to a new isolated `restore-test` directory and compares the complete restored inventory. Only then is `verified.json` written. This proves byte recovery, not Minecraft gameplay compatibility or durability against power loss. No compression, encryption, deduplication or off-host export is implemented. Archives contain secrets from game configuration: restrict access and include them in capacity planning. Failed/incomplete directories remain evidence and are never treated as verified backups.

Scheduling is serial with no overlapping ticks, minimum 60-second intervals and immediate initial attempts after worker startup. Failed jobs do not prevent later jobs. Shutdown stops new jobs and lets active work finish; force termination preserves the lock. Scheduling timestamps are in memory, so restart attempts run immediately. Bounded JSON logs report only instance ID, outcome and successful archive ID. Connect these local logs to the operator's approved alert receiver and monitor worker liveness; no external notification destination is configured automatically.

Retention deletion defaults off. Enabling `allowRetentionDeletion` is explicit approval of that job's retention policy. Pruning considers only recognized archive names with restore markers and currently valid inventories, only after a new restore-tested replacement. It preserves unknown, damaged and incomplete evidence. Review disk usage separately because retained failures can fill storage. Cleanup of a worker-created temporary restoration removes only that generated directory. On-host copies do not protect against host or array loss.

Restore markers must include the matching instance and a valid canonical UTC restoration timestamp before retention can count or delete them. A damaged replacement marker blocks pruning. The replacement always occupies one retained slot, even after wall-clock rollback or equal-millisecond archive naming. Archive-root links are rejected before reading manifests; ancestor directories remain trusted. Overlap checks use native path semantics, including Windows case aliases and filesystem roots.

An archive's `verified.json` records byte restoration, while the worker's `verified` outcome also requires successful lock release. If release fails, the worker reports `failed` and preserves the lock and verified archive for investigation. A restore marker alone does not mean lifecycle ownership was released.

## Recovery and Minecraft acceptance

1. Approve and gracefully stop Minecraft through existing lifecycle controls. Verify exit zero, no OOM and expected persistent volume. Do not accept a forced kill as a consistent world backup.
2. Run the approved worker configuration using `npm run start:backup`; inspect a `verified` report and matching archive marker. Confirm a running server produces a failure rather than a purported backup.
3. Restore into a fresh, absent directory: `node apps/backup-worker/main.mjs restore /archives/minecraft-survival/ARCHIVE_ID /approved/fresh-restore minecraft-survival`. The command verifies inventory and refuses to overwrite an existing directory. It does not touch an active volume.
4. With explicit operator authorization, provision an isolated test volume/container using the same pinned image and world version, copy the restored data and set reviewed ownership. Do not publish production ports or reuse the active world. Launch, connect with a client, check known builds/player state, save and stop gracefully. Record evidence before calling live recovery accepted.
5. Production replacement/restoration requires separate approval, a preserved current-world snapshot and a rollback plan. Never copy onto the active volume from this CLI.

Local tests use a Minecraft-shaped `level.dat` fixture and simulated inspection. They cannot establish real world consistency, game compatibility, firewall isolation, socket permissions, sustained I/O overhead or power-loss durability. Actual Linux acceptance and restore gameplay remain deployment gates.
