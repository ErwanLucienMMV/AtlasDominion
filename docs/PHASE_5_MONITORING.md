# Phase 5 — Monitoring and lifecycle recovery

This phase supplies deployable configuration and runtime code; it does not authorize production deployment. No existing application, game, firewall rule or volume is changed by checking these files. Phase 6 backups remain separate.

## Runtime behavior

Recovery hardening: the 64 KiB event limit applies to each newline-delimited byte frame, including any partial frame retained between reads. A transport chunk may contain many valid frames exceeding 64 KiB in total. UTF-8 decoding occurs only after a complete frame arrives. Shutdown prevents subsequent sampling requests and publication of samples from in-flight reads; already-issued reconciliation/Engine reads are not cancelled. Resource samples require finite, nonnegative memory and cumulative CPU values; zero remains valid.

Audit replay validates every retained record before applying intent: object shape, valid UTC timestamp (seconds or milliseconds), instance identifier, operation name, known outcome and null or sanitized error category. Malformed records block startup without modifying history, including malformed records for unknown instances or ignored operations. Valid records for unregistered instances and operations other than start/stop remain readable but do not change desired state.

The controller opens a Docker container-event stream through a separate Dockerode client. Events trigger inspection of the validated registry; event names, labels and IDs never authorize an operation. Chunked newline-delimited JSON is bounded to 64 KiB. Malformed/oversized frames disconnect and retry after one second. A 15-second periodic pass repairs missed events and daemon reconnect gaps. Only one observer pass runs at once. Engine requests use the existing configured lifecycle timeout; an event-stream connection failure does not stop periodic reconciliation. Shutdown closes the stream and timers.

Reconciliation rebuilds resource reservations from actual approved containers without creating or restarting them. Startup replays the existing append-only daily audit files, in filename/append order, to recover the most recent accepted start/stop intent for registered IDs. Replay is read-only and does not replay operations. Missing history yields unknown intent; malformed history fails startup closed for operator investigation. Preserve the audit volume across controller restarts. Removing retained audit history can remove old intent, so archive history rather than deleting it until a reviewed state snapshot/retention strategy exists. No automatic audit deletion is implemented.

An observed running-to-exited/dead/missing transition increments an unexpected-exit counter unless an accepted stop is intended. Repeated inspection does not increment it again. A fresh controller does not fabricate historical crashes. The persistent-intent alert detects an instance intended to run but stopped after a controller restart. Authorized stops set wanted-stopped before invoking Docker and do not trigger crash alerts. Abnormal stop results still fail existing lifecycle checks; intended stop is not proof of a clean game save. Operator stops outside this API have no persisted intent and may alert; acknowledge these maintenance events operationally.

`GET /metrics` is private and authenticated. The Phase 5 override requires a separate random, at least 32-byte metrics credential; it must differ from the lifecycle credential. Prometheus receives only the metrics credential. Metrics credentials cannot call `/v1/*`; lifecycle credentials cannot scrape when separate credentials are configured. Older controller configurations without `METRICS_SECRET_FILE` retain their existing service credential for compatibility; deploy the override to establish separation.

Metrics contain stable registry instance/game-type labels and fixed operation/state/resource categories. No caller, request, Docker ID, container name, payload or secret becomes a label. Instance info/state series include stopped and missing instances. Counters reset on controller restart; Prometheus `rate`/`increase` handle resets. Completed/failed/timed-out admitted operations are counted; rejected preflight requests are not terminal operations. No durable operation replay/idempotency across process restarts is claimed.

Running approved containers are inspected again before read-only `stats({stream:false})` calls. CPU is cumulative seconds; memory is raw Docker usage bytes including cache. Unavailable/stopped samples are omitted. Host measurements come from Node Exporter; admission reservations are planning budgets, not observed host utilization. This provides generic container monitoring without introducing cAdvisor or granting another service Docker socket access. CPU rate can exceed one core. Polling many instances is sequential; measure pass time and adjust freshness alert thresholds if necessary. Metrics retain last successful observations during Engine outages; consult controller-ready and reconciliation timestamp before treating them as current.

## Operator setup and security review

1. Inventory Linux host resources/listeners and confirm the existing port 4242 workload. Review locally available, version/digest-pinned Prometheus, Grafana and Node Exporter images. Compose rejects missing image inputs but cannot validate their provenance or reject floating values; operators must review them. No images are pulled automatically (`pull_policy: never`).
2. Review `infrastructure/monitoring/compose.json`. All services have no published ports. Prometheus/Node Exporter join only `atlas-monitoring`; Grafana also joins `atlas-proxy`. Existing external networks must already exist. No game networks or volumes are mounted. No service receives the Docker socket.
3. Node Exporter alone mounts `/` read-only with `rslave` propagation and uses host PID visibility to observe the host filesystem. This is broad host visibility, even without privileged mode/capabilities, and requires explicit deployment review. Non-root mount permissions can leave some filesystems unobservable; verify the selected image on the actual Linux host. Network address collectors are disabled; review all exported labels and host mounts for sensitive metadata. Monitoring access is restricted to trusted operators.
4. Prepare uniquely named external Prometheus/Grafana/audit volumes only after approval; never reuse unknown data. Review ownership for Prometheus UID 65534, Grafana UID 472 and the chosen controller image user. Do not recursively change ownership of existing data. Preserve any pre-existing audit files through a separately reviewed migration before activating `/audit`. Set protected controller configuration `auditDirectory` to `/audit`; preserve measured capacity, allowlists, bindings and timeouts from Phase 2.
5. Use protected, untracked environment/configuration files. Set `PROMETHEUS_IMAGE`, `GRAFANA_IMAGE`, `NODE_EXPORTER_IMAGE`, `PROMETHEUS_DATA_VOLUME`, `GRAFANA_DATA_VOLUME`, `METRICS_RETENTION` (for example `7d`), `METRICS_RETENTION_SIZE` (for example `1GB`), `GRAFANA_ADMIN_USER` (non-default), `GRAFANA_ROOT_URL` (approved HTTPS origin), `GRAFANA_PASSWORD_FILE`, `METRICS_SECRET_FILE`. Retention examples are not measured production budgets. Supply `CONTROLLER_CONFIG_FILE`, `CONTROLLER_AUDIT_VOLUME` and the existing application-stack variables for the override. Create unique high-entropy Grafana and metrics secrets; never commit them.
6. Review both resolved configurations with the read-only commands below. The override merges mounts/secrets without removing socket, registry or control-network wiring. Relative paths in overrides resolve against the first Compose file. Absolute operator paths avoid ambiguity. Approve resource limits based on actual monitoring overhead and reserve this capacity outside game admission budgets.
7. Obtain approval before starting these selected services or restarting the controller with its override. No stack-wide recreation, image pull, firewall change or volume deletion is implied. Running games continue independently of the controller.
8. Inspect `grafana-route.example.json`, replace its deliberately invalid hostname with a reviewed dedicated DNS hostname and ensure `GRAFANA_ROOT_URL` matches. Add the reviewed route as a separate File Provider file using the existing Traefik HTTPS resolver; do not replace existing routes. No HTTP Grafana route or host port is provided. Verify login, strong unique credentials, anonymous access disabled and sign-up disabled before exposure. Use least-privilege operator accounts. Native Grafana login supplies mandatory authentication; do not grant general Discord members access to the host datasource. Grafana viewers can query the entire configured datasource, not just this dashboard.

```sh
docker compose --env-file <protected-file> -f infrastructure/monitoring/compose.json config
docker compose --env-file <protected-file> -f infrastructure/applications/compose.json -f infrastructure/monitoring/controller.override.json config
node --test infrastructure/checks/compose.check.mjs infrastructure/checks/monitoring.check.mjs
```

Grafana provisions the private Prometheus datasource and a generic dashboard. Its server selector discovers `atlas_instance_info` labels automatically; no game name is embedded in dashboard queries. Prometheus honors the controller's stable `instance` labels rather than replacing them with its scrape address. Bounded Prometheus storage requires approved retention and size inputs. Audit files are sanitized and permission-restricted; deletion remains a separate approved operation. Review disk space and Grafana data growth independently. Secrets are not passed as command-line literals. Prometheus still has private operational metadata; it must not be routed publicly.

## Alerts and live acceptance

Rules cover controller health, disconnected events, stale reconciliation, unexpected exits, prolonged operations, admission pressure, measured host CPU/RAM/disk pressure and unavailable host exporter. Deliberately stopped instances do not alert as crashes. Rules evaluate in Prometheus and appear in its Alerts page/Grafana Explore; external notification delivery is not configured. Select a notification receiver before relying on unattended paging. Backup, TLS expiry and end-to-end Discord synthetic probes require their own later integration; no misleading placeholder signals are emitted.

On the approved host, record image digests, redacted config, date, operator and each result:

1. Run `promtool check config /etc/prometheus/prometheus.yml` and `promtool check rules /etc/prometheus/alerts.yml` using the selected installation. Check real Prometheus target health and rule loading, Grafana provisioning and HTTPS login. No anonymous dashboard access; Controller/exporter/Prometheus ports unreachable externally.
2. Verify multiple registered arbitrary game types, including a second instance of one type, appear in the selector and state panels without dashboard/code changes. Verify measured Docker stats and host measurements against read-only host inspection.
3. Start/stop through signed authorized Discord requests; inspect terminal counters/audit, age, desired/observed state and reservations. A deliberate clean stop must not fire either unexpected-exit alert. Replays must not increment completed counters twice.
4. In an isolated disposable fixture only, obtain approval for an unexpected exit. Check transition counter and wanted-running alert. Never kill a production game to test monitoring. Acknowledge/recover manually; no auto-restart is implemented.
5. With a fixture running, restart only the controller through the approved workflow. Confirm same game container remains running, intent is replayed and reservations/state recover. Repeat with a deliberately stopped fixture: no crash alert after restart.
6. Test approved daemon/event-stream interruption in an isolated environment. Verify stream health alert, periodic recovery, stale reconciliation alert where appropriate, and eventual fresh state. No stale metrics should be mistaken for successful control.
7. Compare admission-pressure and measured-host-pressure panels/rules using synthetic rule input, without exhausting production resources. Check audit failure blocks admission and appears as controller-unready/audit-pending.
8. Confirm existing port 4242 service and game persistence remain intact. Retain redacted evidence and storage/retention decisions. No local mock test establishes these live properties.
