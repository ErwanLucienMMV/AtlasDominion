# Phase 7 — additional game integrations

V Rising, Project Zomboid and Palworld each have an independent Compose project and matching deny-by-default registry example under `infrastructure/games/`. The controller, Discord API and backup worker retain their generic implementations. These are reviewed integration candidates; no image execution or gameplay acceptance has been performed.

## Image and compatibility review

Upstream sources checked on 2026-10-25:

| Game / candidate image | Native published ports | Persistent data selected for stopped-volume backup | Additional storage |
|---|---|---|---|
| V Rising / `trueosiris/vrising` | 9876, 9877 UDP | `/mnt/vrising/persistentdata` | Separate installation volume at `/mnt/vrising/server` |
| Project Zomboid / `renegademaster/zomboid-dedicated-server` | 16261, 16262 UDP | `/home/steam/Zomboid` | Separate installation volume at `/home/steam/ZomboidDedicatedServer` |
| Palworld / `thijsvanloef/palworld-server-docker` | 8211, 27015 UDP | `/palworld` (installation and saves) | Included in data volume; plan backup capacity accordingly |

Sources: [V Rising image](https://hub.docker.com/r/trueosiris/vrising/), [V Rising entrypoint](https://github.com/TrueOsiris/docker-vrising/blob/master/start.sh), [Zomboid image and ports](https://github.com/Renegade-Master/zomboid-dedicated-server), [Zomboid shutdown implementation](https://github.com/Renegade-Master/zomboid-dedicated-server/blob/main/src/run_server.sh), [Palworld image and non-root operation](https://github.com/thijsvanloef/palworld-server-docker).

All stacks target Linux AMD64, matching the documented host CPU. Require a locally available, reviewed image digest via `VRISING_IMAGE`, `ZOMBOID_IMAGE` or `PALWORLD_IMAGE`; Compose's nonempty-variable check does not certify a digest. Inspect architecture, entrypoint and provenance of that exact digest before approval. An image digest does not pin Steam-downloaded server files. Record server build IDs and matching client releases and retain approved installation data for rollback. Zomboid explicitly requires a reviewed `ZOMBOID_GAME_VERSION` branch; branches can move. V Rising and Zomboid upstream wrappers update server files at startup. Starting them requires approval of that behavior and a recovery snapshot. Palworld disables update-on-boot and scheduled updates after initial installation.

The numerical UID/GID is explicitly `1000:1000` with all capabilities dropped, no privilege escalation and no management networks or socket. Prepare **new** external volumes for this account, checking the selected image's account and writable startup paths first. Never recursively change ownership of existing data. V Rising's upstream wrapper was written with root assumptions (`usermod`, `/root/.steam`) and runs the Windows server through Wine/Xvfb. `HOME` and `WINEPREFIX` select writable steam-user paths, but this does not prove rootless compatibility. Treat V Rising as blocked for deployment until an isolated run demonstrates startup and shutdown with these restrictions. If it needs a derived image or alternate wrapper, review that separately; do not relax controller isolation. Zomboid also writes startup files under `/home/steam`; verify ownership in the pinned image. Palworld documents overriding the default root user; verify its non-root initialization and writable script directories with the selected digest.

The runtime identity verifier now enforces `CapDrop` containing `ALL`, no added capabilities, and enabled `no-new-privileges` on every inspected game, including Minecraft and generic instances. It rejects explicit `seccomp=unconfined` (and the legacy colon form), device mappings, device requests and device cgroup grants. Missing capability-drop or privilege controls fail with `IDENTITY_MISMATCH`; nullable empty optional grant lists remain valid. Docker's bare, colon-true and equals-true no-new-privileges forms are accepted, while conflicting false values are refused. This follows [Docker security option semantics](https://docs.docker.com/reference/cli/docker/container/run/#optional-security-options---security-opt). Existing provisioned games missing these controls now fail verification and need separately approved provisioning review; the controller does not modify them. This is inspection-level enforcement, not certification of daemon defaults, custom seccomp profiles or host kernel isolation.

## Operator configuration

For each stack set its uppercase prefix (`VRISING`, `ZOMBOID`, `PALWORLD`) variables in a protected untracked environment file: `_IMAGE`, `_MEMORY_LIMIT`, `_CPU_LIMIT`, `_BIND_ADDRESS`, `_DATA_VOLUME`, and `_INSTALL_VOLUME` where applicable. Review the complete resolved plan using `docker compose --env-file <protected-file> -f infrastructure/games/<game>/compose.json config`. Rendered configuration may contain secrets; never publish it.

Zomboid additionally requires `_HEAP`, `_GAME_VERSION`, `_ADMIN_PASSWORD`, `_RCON_PASSWORD` and `_SERVER_PASSWORD`. Palworld requires `_ADMIN_PASSWORD` and `_SERVER_PASSWORD`. V Rising uses persistent `Settings/ServerHostSettings.json` for private access/password policy; set and verify it before admitting players. Keep image logs private and do not enable shell debug logging. Example memory/admission budgets (8 GiB V Rising/Zomboid, 16 GiB Palworld) and CPU budgets are planning placeholders, not measured requirements. Set Docker limits and manifest expectations together after measuring the existing port 4242 workload and host headroom. These examples do not authorize running all games simultaneously.

Only native UDP is published; RCON and REST administration ports stay internal. Zomboid keeps internal RCON configured so the image's SIGTERM handler can send `quit`. Palworld keeps internal REST/RCON for its shutdown wrapper, with a private admin password, and disables built-in scheduled backups/restarts/pause/sleep so they do not compete with lifecycle ownership. These endpoints remain reachable within the game's own bridge; do not attach untrusted containers. V Rising uses the upstream Wine signal handler. Verify save completion and clean exit for every pinned wrapper; exit zero alone does not certify a saved world.

Generic `docker-stop` forwards SIGTERM. Compose allows 120 seconds; configure the controller's global `stopTimeoutSeconds: 120` and `timeoutMs: 180000` or a larger measured pair. Dockerode's explicit timeout overrides Compose's grace period. Review compatibility with Minecraft's existing save window when changing global settings. No forced kill is an acceptable persistence test. Readiness deliberately remains `unverified`; neither a running container nor an open UDP port establishes gameplay.

## Provisioning and live acceptance — required for each game

Follow [onboarding](ADDING_A_GAME.md) and obtain deployment approval before pulling images, preparing volumes, creating containers or starting games. Do not activate these examples automatically. Record operator, date, host, exact image digest, Steam build/client version, container ID, volume names, resource settings and pass/fail evidence separately for each game.

1. Inventory disk/CPU/RAM and native port availability; preserve the existing application and independent stacks. Review rootless compatibility and licenses. Prepare unique new external volumes and an isolated test installation with approved network access for Steam downloads.
2. Review the resolved plan, then use only the approved stack's `create --no-deps <service>` to pre-create a stopped container. Inspect exact labels, non-root account, limits, native mappings, private network, restart `no` and persistent mounts. Never recreate an unknown existing container.
3. Copy only manifests into a candidate registry directory, configure measured budgets and explicit Discord allowlists, and validate the entire registry set. The checked-in examples authorize nobody. Activate through an approved controller restart with matching bind-address allowlist. Check list/status/autocomplete and unauthorized/unknown rejection before enabling players.
4. Start through a real signed Discord interaction; check private acknowledgement, audit completion, status and idempotent start. Confirm readiness stays `unverified`. Use a matching external game client: V Rising direct-connect to port 9876, Zomboid join at 16261 with 16262 reachable, Palworld direct-connect to 8211. Actually join/play; port scanning is insufficient.
5. Create a recognizable persistent marker: V Rising castle/player state; Zomboid character inventory and a placed item; Palworld character/base/Pals. Record private evidence. Stop through Discord, inspect save logs and exit zero/no OOM/no forced termination. Repeat stop for idempotency. Restart the **same container and volumes**, rejoin and verify marker/configuration persistence.
6. Confirm generic `/metrics` series contain the instance ID and game type, Grafana selectors discover it and resource samples populate. An intentional stop must not raise an unexpected-exit alert. Restart only the controller through the approved process while the game runs and verify reservation/status recovery and subsequent control. Verify application health throughout.
7. Configure backup jobs and perform isolated game recovery as below. Grant player access only after all gates pass. Record failures rather than treating mock tests as acceptance.

## Backup wiring and recovery

Use [Phase 6 coordination and recovery](PHASE_6_BACKUP.md). Add each instance to protected worker settings with `instanceId`, a unique read-only mounted `source`, separate `destination`, actual external `volumeName`, and the data path from the table as `containerPath`. The worker must mount the same persistent lock directory as the controller. Retention deletion remains false until explicitly approved. Installation-only volumes for V Rising/Zomboid are excluded from the world archive: retain the exact game build separately. Palworld's full volume may contain symlinks from Steam installation; the worker rejects links/special files. Inspect it before enabling backups. If incompatible, review a separate saves-only named volume and matching worker job rather than weakening archive validation.

`infrastructure/backup/phase7.override.json` adds the three existing external data volumes as read-only sources when merged after the Phase 6 worker Compose file. It does not start any service. `phase7.settings.example.json` supplies matching jobs; replace every volume placeholder with the actual external volume name and review schedules/capacity. Each destination is a sibling under `/archives`; the worker adds the instance ID again beneath that job destination. If retaining the existing Minecraft job, change its destination to a separate sibling such as `/archives/minecraft-survival` through reviewed operator configuration. A job targeting the parent `/archives` conflicts with the new children and is correctly rejected. Keep the Minecraft source mount and job if still required. Do not replace active worker settings with this three-game example and lose its existing jobs.

After a clean saved stop, require a `verified` worker report and matching restore marker. Verify a running instance is refused. Restore using `node apps/backup-worker/main.mjs restore <archive> <fresh-absent-directory> <instance-id>`; the command never overwrites a live directory. With separate approval, copy into a new isolated volume, review ownership, and launch the same pinned image/server build with different identity and nonproduction ports. Join with a client and verify the marker and player state, save and stop again. A byte-perfect mock restore is not proof of game recovery. Never restore over the active volume or delete recovery evidence during acceptance.

Before restoration verification, the worker repeats the approved volume type/name/destination check on the post-copy pinned inspection. Inconsistent metadata fails the job, emits no successful report or verification marker, preserves copied evidence and source data, and releases the lifecycle lock normally. This closes a simulated consistency gap; it does not establish that Docker permits mounts to change on an unchanged container ID.
